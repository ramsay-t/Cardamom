A Supervision tree

One :one_for_one supervisor owns the long-lived processes. Per-peer sessions and per-block/header handlers are spun up dynamically underneath their own supervisors, so a crash is isolated to one peer or one block.

B One peer session

C The validation pipeline

This is the heart of "can it validate". A header passes a decode → validate → store gate; a block body passes a build-delta → verdict → commit gate. Every rule returns a result; the verdict decides accept/reject; nothing derived commits on a reject.

One rule set, three policies. The same TxValidation.run runs on block txs (assert / stop-and-fix), on a replay (halt), and — next — on mempool txs (predict). A reject on real chain data means our derivation is wrong.

D Where state lives

Chain data and derived ledger state are different stores. The forest holds candidate branches; ChainStore fronts SQLite with a cache; ledger state is a current-value set plus an invertible per-block delta journal, so rollback is a normal operation run backwards.

chain data · truth

ChainStore → SQLite + Cache

Headers & blocks verbatim (hash fidelity) plus decoded columns. Nebulex cache fronts the durable Ecto/SQLite store.

belief · candidates

Forest.Server

Candidate-chain forest keyed by hash, indexed by parent — tolerant of out-of-order arrival, forks and gaps.

derived · foldable

Ledger state

UTxO set + non-UTxO accounting (rewards, deposits, pots, :pparams, :gov) as invertible delta ops in a k-bounded journal.

read-only

Web UI · Stats · Peers

Observe node state through clean read-only seams and the telemetry spine; never drive the node.
